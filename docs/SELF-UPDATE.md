## Why it carries a copy of its own code — and why it still reads GitHub

Both are true at once. The earlier answer that "Vorv can't read GitHub" was
wrong, and it is worth saying exactly what the copy is for:

- **GitHub is readable.** `self_update` with `action: read_source, from: github`
  fetches a file's text from `main` through the contents API. Reading and
  pushing use the same key.
- **The shipped copy is the code that is running.** `app/src/main/assets/source`
  is a copy of the source packaged into the APK. `self_fix` swaps a class at
  runtime, so it must patch the code this installed build was compiled from.
  `main` can be ahead of that: a change can be pushed and not yet built, tested
  or installed. Patching from `main` in that window gives a patch that does not
  match the running class, which is the failure mode the copy prevents.
- **When the two differ, Vorv says so.** `read_source, from: github` reads both
  and prints a line saying they differ, which one the phone runs, and that the
  app stays as it is until a new build is installed. Neither copy is passed off
  as the other.
- **A change writes one file.** `push` writes the source file only. The copy in
  `assets/source` is generated by the build from `app/src/main/java` and is
  git-ignored since 0.9.37, so there is no second file to keep in step: the
  copy in the APK is always the code that was compiled into it.

## What Vorv can already do with no help from the owner

1. **Rewrite one of its own classes and run the rewrite.**
   `self_fix` (and the crash dialog's "Attempt self-repair") takes a problem in
   words, has the on-device coder model write the complete class, compiles it
   inside the app with Vorv's own compiler (`ForgeCompiler`, shipped in the
   APK), checks that every public constructor, method and field of the original
   survived (`PatchVerifier`), signs the result with a device key, asks once for
   the whole plan, and applies it at the next start through a class loader that
   shadows the app's own class (`HotPatcher` + `PatchRegistry`). A crash in the
   patched class within 72 hours rolls it back automatically.

2. **Reach exactly 20 classes.** That is the honest limit: a patch only runs
   where the app builds the object through `PatchRegistry.create`. Those 20 are
   the agent's tools, `CognitiveKernel`, `HealingAgent` and now `SelfUpdateTool`.
   Screens, storage and the builder itself have no dispatch point, so a patch
   for them would compile, be signed, and never run. `self_fix` refuses them
   instead of pretending.

3. **Build other apps.** `build_app` compiles Java projects on the phone into a
   signed APK, and `native_test` installs and drives them. That pipeline cannot
   build Vorv itself: Vorv needs Compose, Kotlin resources and a resource table,
   and the arm64 `aapt2` builds that exist are host binaries that need glibc.

## What only the owner can do (one time)

1. **Create one GitHub token.** GitHub → Settings → Developer settings →
   Personal access tokens → **Fine-grained tokens** → Generate new token →
   Repository access: **Only select repositories** → `thepotatoninjahost/Stupid-agent`
   → Permissions → Repository permissions → **Contents: Read and write** →
   Generate → copy the token.
2. **Paste it once** into Vorv: Setup → **Self-modification** → paste → Save key.
   It is stored in the same encrypted, Keystore-backed store as the model keys
   (`SecretsStore`), is never shown again, and can be revoked on GitHub at any
   time.
3. **Add one more permission to the same token: Actions: Read.** On the token's
   page: Permissions → Repository permissions → **Actions** → Read. This is what
   lets Vorv see a build that *failed* and name the step that failed, from the
   phone, instead of leaving the owner to open GitHub on a computer. Without it
   every other action still works; `check` just cannot say why a build failed.
4. That is all. Deleting the token on GitHub switches the writing half off
   again; reading builds keeps working without it.

## What was built on 2026-11-28 (the half that needs no key)

- `host/vorv/selfupdate/GitHubRepo.kt` — reads the repository head, reads a
  file's text ([getFile]), reads and replaces a file through the contents API,
  reads the rolling `ci-latest` release, streams its APK down, and reads the
  build's own workflow run and the steps that failed. A 409 (the file changed
  under it) is retried once with the fresh blob id, then reported; it never
  overwrites another change silently.
- `host/vorv/selfupdate/SelfUpdate.kt` — the rules: the one path rule that
  maps a source file to its shipped copy under `assets/source` (generated by
  the build, git-ignored); an update APK is only offered
  to the installer after Android's own three conditions are checked in advance —
  same application id, same signing certificate, version code not lower; and
  when the shipped copy and GitHub differ, `driftNote` says so instead of
  letting one stand in for the other.
- `host/vorv/tools/SelfUpdateTool.kt` — the agent tool `self_update` with five
  actions: `status`, `read_source` (`from: shipped` or `from: github`), `push`,
  `check` (now also reports whether the build is running, succeeded or FAILED,
  and which step failed), `install`. `push` and
  `install` each ask the owner in the consent dialog; without the consent
  bridge they refuse (fail closed). A push writes the source file only; the
  shipped copy is the build's job.
- Setup → Self-modification: the token field and the saved/not-saved state.
- `PatchRegistry` now dispatches `SelfUpdateTool` too, so the tool is inside the
  repairable surface like every other tool.

## What the loop does, in order

```
read_source (the exact code this build shipped)
  → the model writes the complete changed file
  → push        (one commit: the file)
  → GitHub Actions: full unit tests, then assembleDebug, then the ci-latest release
  → check       (is the build running, did it fail at a named step, and does the
                 newest release name that commit?)
  → install     (download, prove it is Vorv, then the system installer)
```

A failed build publishes nothing, so a broken change can never install by
itself. The installed app is only ever replaced by an APK with the same package
name and the same signing key, and Android's installer still asks.

- No real push, no real release read from the phone, no APK download, no
  install. Those need the token and the device.
- No real call to `getFile`, `latestRun` or `failedSteps`: they are compiled and
  their error sentences are written, but no key with Actions: Read has ever
  called them. The `check` output on a genuinely failed build is therefore
  unverified until the first failure it reads.

  exercised: it needs a real installed app and a real second APK.
- The 125 MB download over the owner's connection is untested; the read timeout
  is 5 minutes, so a slow connection fails loudly rather than hanging.

## Sources (checked 2026-11-28)

- Update acceptance rules — same application id, same signing certificate,
  version code ≥ installed:
  <https://developer.android.com/google/play/app-updates> ("The application ID
  of the update must be the same as the installed app. The signing certificate
  of the update must be the same as the signing certificate of the installed
  app … The version code of the update must be higher or equal to the version
  code of the installed app.").
- Install sessions, including updating itself:
  <https://developer.android.com/reference/android/content/pm/PackageInstaller>.
- Create or update file contents — `message` and base64 `content` required,
  `sha` "Required if you are updating a file", 409 Conflict, 422 Validation
  failed: <https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents>.
- Release asset download — "set the Accept header of the request to
  application/octet-stream. The API will either redirect the client … API
  clients should handle both a 200 or 302 response":
  <https://docs.github.com/en/rest/releases/assets#get-a-release-asset>.
- Get repository content returns a file base64-encoded in JSON — example
  response shows `"encoding": "base64"` and a wrapped `content` string:
  <https://docs.github.com/rest/repos/contents>. The base64 GitHub wraps in
  newlines has to be unwrapped before decoding.
- Workflow runs — `GET /repos/{owner}/{repo}/actions/runs` and the run's jobs:
  <https://docs.github.com/en/rest/actions/workflow-runs>.
- Which permission those endpoints need — the fine-grained permission table
  lists `GET /repos/{owner}/{repo}/actions/runs` under the Actions permission
  at read:
  <https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens>.
- `releases/latest` excludes prereleases, which is why the rolling build is read
  by tag: <https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name>.
