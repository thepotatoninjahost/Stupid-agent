## 1. What to fix first

**The self-repair system does not repair anything, and it tells the user it did.**
Every hot patch is loaded through a parent-first class loader whose parent already contains the
class being patched. The loader therefore returns the *original* class, not the patch. The
completeness check compares the original class with itself and always passes, the "does it
implement the dispatch interface" gate always passes, and the consent dialog says
"Verified: full public API kept" and "the patched class replaces the original at the next app
start". None of that is true. The app's own test suite asserts the original class is returned
and still calls the result a success.

**Second: `linux_run` runs arbitrary shell commands on the phone with no consent dialog.**
`ShellTool` fails closed and asks the user; `linux_run` has no `ctx.confirm` call at all. An
injected instruction in a web page or file can make the agent install packages and run commands
silently.

**Third: the network policy does not cover the shell.** `NetworkGuard` is applied to the LLM
clients, the web tools and the in-app browser. It is not applied to the guest shell, so `curl`
inside Vorv's Linux system can reach any host, including LAN and metadata addresses.

Everything else in this report is lower severity. The engineering quality in the rest of the
project is high; the problems are concentrated in the self-repair chain and in the two places
where the sandbox boundary is assumed rather than enforced.

## 5. Details

### C-1 — Hot patches never execute

**Evidence**

- `watchdog/HotPatcher.kt:142` creates the loader:
  `DexClassLoader(dexFile.absolutePath, odexDir.absolutePath, null, context.classLoader)`.
- `watchdog/HotPatcher.kt:153` checks the patch:
  `base.isAssignableFrom(loader.loadClass(fqcn))`.
- `watchdog/PatchRegistry.kt:95` does the same at dispatch time:
  `loader.loadClass(fqcn)`, then `iface.isAssignableFrom(patched)` and `construct(patched, args)`.
- `healer/PatchVerifier.kt:90` builds
  `PathClassLoader(patchDex.absolutePath, appClasspath, originalClass.classLoader)` and loads at
  line 101.

`ClassLoader.loadClass` is parent-first. The parent here is the app's own loader, which already
contains every patchable FQCN. So `loadClass(fqcn)` returns the **original** class in all three
places:

- Gate 6 in `HotPatcher` asks whether the original implements its own interface — always true.
- `PatchRegistry.create` constructs the original class and returns it as the "patch".
- `PatchVerifier` compares the original's constructors, methods and fields with the original's —
  so `missingCtors`, `missingMethods` and `missingFields` are always empty and `ok` is always
  true.

The repository's own test documents this. `PatchRegistryTest.kt:108-121`:

```kotlin
// javaClass.classLoader can load NotifyTool and it implements Tool,
// so dispatch must now succeed with the ORIGINAL class itself.
val tool = PatchRegistry.create(Tool::class.java, "host.vorv.tools.NotifyTool", context)
assertNotNull(tool)
assertEquals("notify", tool!!.name)
```

That test passes because the original class is returned. The other dispatch test
(`interface dispatch accepts a cross-loader implementor`) only asserts
`Tool.isAssignableFrom(proxy.javaClass)` and never calls `create`, so it does not test dispatch
at all.

I confirmed the parent-first semantics with a JVM experiment: a child `URLClassLoader` whose
parent holds the same FQCN returned the parent's class object (`same Class object as parent's:
true`).

**Impact**

Self-repair is theatre. The app compiles a patch, signs it, stores it, asks the user to approve,
tells the user to restart, and then runs the original code. The user-visible claim "the patched
class replaces the original at the next app start" is false. A crash the healer claims to fix
will recur. The only real effect is that the app spends CPU and storage producing dex files that
are never used.

**Fix**

Load the patch class in a loader that does **not** delegate to the app loader for the patched
FQCN, or inspect the dex directly:

- Build the verification loader with `parent = null` (or a loader that excludes the app's dex),
  and add the app classes only as a *library* path, not as the parent. Then assert
  `loaded.classLoader !== originalClass.classLoader` and that the loaded class's declared
  members come from the dex.
- For dispatch, `PatchRegistry.create` must construct the class from the patch dex, not from the
  parent. Store the patch dex path and instantiate with a child-first loader; or read the dex
  with `DexFile` and instantiate through it.
- Replace the test at `PatchRegistryTest.kt:117` with one that asserts the returned object is
  **not** the original class (for example, a patch class whose `name` differs) and that its
  class loader is the patch loader. Add a test that calls `PatchVerifier.verify` with a dex that
  omits a public method and asserts `ok == false`.

This is a design change in the patch loader, not a one-line fix. It should be planned and
tested on a device.

### C-2 — The self-repair consent text and success message are false

**Evidence**

- `healer/HealingAgent.kt:283` sets `surfaceVerified = true` unconditionally, after the
  tautological check in C-1.
- `MainActivity.kt:582` renders
  `"• Verified: ${if (p.surfaceVerified) "full public API kept" else "NOT verified"}"`.
- `MainActivity.kt:585-586` promises "the patched class replaces the original at the next app start".
- `tools/SelfFixTool.kt:247` repeats the same "Verified: full public API kept" line, and
  `SelfFixTool.kt:265` tells the model "VERIFIED (complete public API kept) ... It becomes active
  at the NEXT APP START".

**Impact**

The user approves a patch based on a verification claim that cannot fail. The LLM is told the
repair succeeded and repeats that to the user. This is a trust failure, not just a bug: the
dialog is the only control the user has over code injection into their own app.

**Fix**

- Make `surfaceVerified` the actual result of a verification that can fail (see C-1).
- Until C-1 is fixed, set it to `false` and change the text to say the patch is unverified.
- After C-1, keep the text honest: "verified against the previous class's public API" only if
  the check really compared against the previous class.
- Add a test that a patch missing a public method is rejected and that the dialog text says so.

### H-1 — `linux_run` runs arbitrary commands with no consent

**Evidence**

- `tools/LinuxRunTool.kt:18` defines `name = "linux_run"`; line 71 emits a citation saying it ran
  "inside Vorv's Linux system".
- The file contains no `ctx.confirm` call (`grep -n confirm` returns nothing).
- It is registered at `AgentViewModel.kt:250`.
- By contrast, `ShellTool.kt:88` calls `ctx.confirm` and fails closed when the bridge is absent;
  `ConsentGate.kt:44-47` treats silence as "no".

**Impact**

The agent can run any command in the guest — `apt-get install`, `curl`, file operations — without
the user seeing it. A prompt injection in a web page, a document or a project file can turn into
silent command execution on the phone. The tool's description advertises `apt-get install -y`
as a normal action, which makes this easy to reach.

**Fix**

Require the same consent as `ShellTool`, or remove `linux_run` and route everything through
`ShellTool`. If the tool is kept, add a `Tool` risk/consent flag so the kernel enforces consent
centrally instead of relying on each tool to remember. At minimum, add
`ctx.confirm ?: fail(...)` and deny when the user says no.

### H-2 — The guest shell bypasses `NetworkGuard`

**Evidence**

- `NetworkGuard` is referenced in `AgentViewModel.kt`, `llm/Llm.kt`, `tools/BrowserAutomateTool.kt`
  and `tools/WebTools.kt`.
- `grep` finds no `NetworkGuard` reference in `ShellTool.kt`, `LinuxRunTool.kt`, `GuestShell.kt`
  or `linux/LinuxSystem.kt`.
- `NetworkGuard` is an OkHttp `Dns` plus a pre-navigation host check; it governs Java HTTP
  clients and the WebView, not a subprocess.

**Impact**

The stated network policy ("no private addresses") does not apply to commands run in the guest.
`curl http://192.168.x.x/...` or `curl http://169.254.169.254/...` from the guest is not checked.
This is confirmed by construction; I did not run it on a device.

**Fix**

Enforce the policy at the network layer, not in each client: run the guest behind a proxy or a
network namespace with a DNS resolver that refuses private ranges, or add a hosts/DNS blocklist
inside the rootfs. Document that the guest is not covered until that exists. Do not rely on
`NetworkGuard` for the shell.

### H-3 — `web_test` does not check sub-resource requests

**Evidence**

- `web/WebAppHarness.kt:83` installs a `WebViewClient` that overrides only `onPageFinished`.
- `grep` finds no `shouldInterceptRequest` in that file.
- `tools/BrowserAutomateTool.kt:309` does override it and delegates to the original client after
  its own check.

**Impact**

`web_test` loads a project page and its sub-resources. The top-level navigation is checked (if
the harness uses the guarded client), but a page can fetch a LAN address, a metadata endpoint or
a file URL through an image, script or fetch call without a per-request check. The two browser
surfaces have different security properties, which is easy to miss.

**Fix**

Reuse the `GuardWebViewClient` from `BrowserAutomateTool` in `WebAppHarness`, or extract it to a
shared class. Add a test page that fetches a blocked host and assert the request is refused.

### H-4 — Provider exchange metadata is included in cloud backup

**Evidence**

- `llm/Llm.kt:237` reads the response body; line 242 calls `BrainState.recordExchange(...)` with
  `url`, `model`, `authorizationSent`, `code` and `body = responseBody.take(600)`.
- `data/VorvPrefs.kt:134` stores it under the DataStore key `brain_facts_json`.
- `backup_rules.xml` and `data_extraction_rules.xml` exclude `vorv.db*`, `vorv_secrets.xml`,
  `crash_logs`, `watchdog` and `healer`, but **not** the DataStore preferences. The comment in
  `data_extraction_rules.xml` says "Settings (DataStore) do transfer."

**Impact**

The provider URL, model name, HTTP status and up to 600 characters of the response body are
uploaded to Google cloud backup. Response bodies can contain user content, prompts and provider
error text. The app's own documentation says conversation and tool data stay local; this is a
gap in that promise. The API key itself is not included (`authorizationSent` is a boolean).

**Fix**

Exclude the `brain_facts_json` key from backup, or keep `lastExchange` in memory only. If the
diagnostic value is needed after a restart, store it in a file under an excluded directory.
Add a test that the backup rules exclude the prefs file or the key.

### H-5 — The LLM client follows redirects and never enforces https

**Evidence**

- `llm/Llm.kt:346-352` builds the shared client with timeouts and `NetworkGuard.PublicDns`, but no
  `.followRedirects(false)` and no `CertificatePinner`. OkHttp follows redirects by default.
- `grep` finds no `isHttps`, `CertificatePinner` or `networkSecurityConfig` anywhere in
  `app/src/main/java` or the manifest; `res/xml/` has no network-security config.
- `llm/BrainDoctor.kt:74` treats a base URL as valid when it starts with `http://` *or* `https://`.
- `llm/provider/BrainTarget.kt:22-30` passes the user-typed base URL through without a scheme check.

**Impact**

A 307/308 from a custom or compromised provider endpoint re-sends the request body — the prompt —
to the redirect target. OkHttp strips `Authorization` on a cross-host redirect, so the key is
usually safe, but prompt content is not. A user-typed `http://` endpoint is refused today only by
the platform default for `targetSdk 35`; there is no application-level guarantee, and one manifest
line (`usesCleartextTraffic="true"`) would remove it. Pinning is absent, so a compromised CA or a
captive portal can intercept provider traffic.

**Fix**

- `.followRedirects(false)` on the LLM client (and the probe), or allow redirects only within the
  configured host.
- Reject a non-`https` base URL in `BrainTarget.resolve` and in `BrainDoctor`, with a clear message.
- Optionally pin the known provider hosts; at minimum document that custom endpoints are trusted.

### H-6 — The fallback patch-signing key and patch artifacts are included in cloud backup

**Evidence**

- `watchdog/PatchKeys.kt:177-184` stores the fallback software private key under
  `filesDir/<FALLBACK_DIR>`, with the comment "filesDir is app-private (0700) on Android — the key
  material never leaves it."
- `backup_rules.xml` and `data_extraction_rules.xml` contain no `domain="file"` exclude. Only
  `vorv.db*`, `shared_prefs/vorv_secrets.xml` and three external directories are excluded.
- The hotpatch directory (`filesDir/hotpatch`, with `approved.json` and the signed dex files) is
  under the same `files` domain.

**Impact**

On devices where the Keystore path is unavailable (the fallback exists for exactly that case), the
patch-signing private key is uploaded to Google cloud backup and transferred to a new device,
contrary to the code's own claim. The signed patches and the approval record go with it. This
undermines the signature gate in `HotPatcher`: whoever can restore that key can sign patches that
the app will accept. Severity is Medium because the Keystore is the primary path, but it becomes
High on any device that falls back.

**Fix**

- Add `<exclude domain="file" path="hotpatch"/>` and an exclude for the fallback key directory to
  both backup rule files.
- Better: store the fallback key under `noBackupFilesDir`, which exists precisely for this.
- Add a test that the backup rules exclude the hotpatch and key paths.

### M-1 — LLM response body is read without a size cap

**Evidence**

- `llm/Llm.kt:237` and `:393` call `res.body?.string()`.
- The failure handler at `:322` catches `Exception`; `OutOfMemoryError` is an `Error`, not an
  `Exception`.

**Impact**

A misbehaving or hostile provider (or a proxy returning a huge error page) can make the app
allocate an arbitrarily large string. The app can be killed by OOM instead of reporting a clear
error. On a phone with limited heap this is easy to trigger.

**Fix**

Read with a byte cap, for example `body.byteStream().readNBytes(MAX_BYTES)` and fail with a
clear message when the cap is exceeded. Cap the error body too. Consider catching `Throwable`
only around the read and converting OOM to a failed response.

### M-2 — GPU bundle import has no size limits

**Evidence**

- `learn/GpuBundleZip.kt:45` and `:48` read `MANIFEST` and `METRICS` with `readText()` and no
  size check.
- `:59-67` copies the `.gguf` entry with a 64 KiB buffer and no cap against `entry.size` or free
  disk space.

**Impact**

A crafted bundle can exhaust memory (manifest/metrics) or fill storage (model copy). The import
is user-initiated, so the risk is lower than a network-driven one, but the file may come from
anywhere.

**Fix**

Cap manifest/metrics (for example 1 MB) and the model size (for example against free space and a
configured maximum). Verify the declared digest and length before writing. Delete the partial
file on failure (already done) and report the reason.

### M-3 — `PatchVerifier.verify` has no test

**Evidence**

- `grep` finds no test calling `PatchVerifier.verify`.
- `HotPatcherTest` tests `PatchKeys.verify` only.
- `PatchRegistryTest` tests dispatch but, as noted in C-1, asserts the original class.

**Impact**

The completeness gate — the mechanism that is supposed to prevent partial patches — has never
been exercised. A test would have caught C-1 immediately.

**Fix**

Add a test with a dex that omits a public method and assert `ok == false`; add one with a
complete dex and assert `ok == true` and that the loaded class is not the original. Run it on a
device or an emulator, since `PathClassLoader` and dex parsing are Android-specific.

### M-4 — The source mirror is generated by the build

**Evidence**

- `app/build.gradle.kts:142-147` registers `syncSourceMirror` (copies `src/main/java` into
  `src/main/assets/source`) and wires it to `preBuild`.
- `SourceMirrorTest.kt` asserts every source file has a mirror and that the mirror has no stale
  or orphan files.
- The mirror directory is tracked in git (135 files) and is not in `.gitignore`.

**Impact**

Because the build regenerates the mirror before tests run, the test cannot detect drift between
the committed mirror and the source. It only checks that the copy just made matches. The 135
source files are also shipped inside the APK, which is unnecessary weight and exposes source to
anyone who unzips the APK (the project is MIT-licensed, so this is not a licensing problem).

**Fix**

Either stop tracking the mirror and generate it at build time (then the test is unnecessary), or
stop generating it and check the committed copy. If the mirror is meant for the on-device
self-repair compiler, keep it but exclude it from the APK if possible, or accept the size and
document why.

### M-7 — The watchdog treats every main-process death as a crash

**Evidence**

- `watchdog/WatchdogService.kt:194-200` calls `onMainProcessDied("binder death")` from
  `linkToDeath`, which fires on *any* main-process death — including the user swiping the app from
  recents or the app calling `killProcess` itself.
- `onMainProcessDied` writes a crash file, then relaunches subject to the 5-per-10-minute circuit
  breaker (`:122-132`).
- The stale-heartbeat path (`checkMainProcessHealth`, `:389-416`) writes a
  `.crash_handled_<ts>` marker to avoid repeating; the binder-death path does not, so the two
  paths can both fire for one death.
- The relaunch uses `startActivity` from a background service, which Android 10+ restricts.

**Impact**

Closing the app on purpose is recorded and treated as a crash: a crash file is written, the app is
relaunched, the restarted app offers self-repair, and the relaunch budget is consumed. Five
ordinary closes in ten minutes trip the breaker, after which crash protection stops until the user
opens the app again. Where background activity launch is blocked, the relaunch silently fails and
the crash file is the only trace. A user who closes the app may also see the crash dialog on the
next open, which is confusing and undermines trust in the healer.

**Fix**

- Distinguish a user-initiated stop: set a "closed by user" flag in `onTaskRemoved` (or check
  `ActivityManager.RunningAppProcessInfo.importance`), and skip the crash path when it is set.
- Use one handled-marker shared by both detection paths, keyed by death/heartbeat, so one death
  produces one report.
- Post a notification instead of (or before) `startActivity` when the app is in the background,
  and state in the crash record when the relaunch was refused.

## 6. Strengths

These are real and worth keeping:

- **CI hygiene.** Actions are pinned by SHA; fork PRs never receive the release keystore;
  release steps are gated to push events; the workflow warns instead of failing when the signing
  secrets are absent. The wrapper distribution is hash-pinned, including a comment explaining the
  mirror outage that motivated it.
- **Secret scan.** No `sk-`, `ghp_`, `AKIA` or private-key material in the working tree; no `.env`
  files. The committed `vorv-debug.keystore` is the debug key only.
- **Consent gate design.** One dialog at a time, silence is "no", and the shell tool fails closed
  when the bridge is unavailable. The mechanism is good; the problem is that not every tool uses
  it (H-1).
- **`ShellTool`.** Command quoting, timeouts, a blocked-session guard and a consent prompt. This
  is the model the other shell tool should follow.
- **JS sandbox.** `JsExecTool` uses a Rhino `ClassShutter` that exposes only its own `Console` helper and
  `java.lang.String`, with a
  time limit and a hardened scope. This looks genuinely well done.
- **WebView hardening.** `BrowserAutomateTool` allows only http/https, disables file and content
  access, and checks every navigation and sub-resource. `WebAppHarness` has the same settings
  (minus the sub-resource check, H-3).
- **Tool call validation.** `ToolCallValidator` checks required fields and JSON types before
  dispatch, and the kernel counts malformed calls against the per-task limit.
- **Test suite.** 776 tests, all green, including tests that pin specific past bugs. The problem
  is not the quantity; it is that the two tests around patching pin the wrong behaviour.
- **Documentation.** `CHANGES.md`, `REVIEW.md`, `CODE-REVIEW.md` and `AGENTS.md` record the
  project's own findings and the reasoning behind fixes. The project is unusually honest about
  its history, which makes this review easier.

## 7. Not covered / limits

- **The APK was not built.** The payload trees are git-ignored and absent; `checkPayload` would
  fail. I did not attempt to fetch the payload.
- **No Android device or emulator.** C-1, H-2 and H-3 are confirmed by construction and by the
  repository's own tests, not by running the app. The `proot` behaviour and the accessibility
  service were not exercised.
- **The UI was not run.** The consent dialog text was read from source; the rendered layout and
  the accessibility flow were not checked.
- **The LLM and learn modules were reviewed at the source level only.** No provider was called
  and no model was trained.
- **The network scan was not run.** `NetworkGuard` coverage was checked by reading call sites.
- **The Forge compiler and runtime subprocess paths** (`forge/ForgeCompiler.kt:134`,
  `forge/ForgeRuntime.kt:110`) were only located by grep, not audited in depth; they appear to be
  reached from `build_app`/`native_test`, which are user-initiated.
- **Helper claims that could not be confirmed were dropped.** In particular, the claim that the
  hotpatch directory is writable through the app's own tool surface is not supported: `FileTools`
  is confined to the SAF workspace and `ShellTool` binds only the workspace. The guest rootfs
  lives at `filesDir/linux/rootfs`, a sibling of `filesDir/hotpatch`, and `proot` is not a
  security boundary, so a guest escape is plausible but was not demonstrated. Treat it as a
  residual risk, not a confirmed finding.
